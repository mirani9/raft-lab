Raft Write & Replication Pipeline
  1. Client Write -> Gateway: POST /write discovers the reachable Leader and forwards the request with an idempotent requestId.
  2. Leader WAL Append: Leader assigns the next log index in currentTerm and persists WAL/state before replicating.
  3. Parallel AppendEntries RPCs: Leader sends entries to peers; followers check log continuity (prevLogIndex & prevLogTerm) and append.
  4. Majority Quorum Commit: Once ackCount >= majority for an entry in the current term, commitIndex advances and entries apply to state.
  5. Snapshot Compaction: At 20 committed entries, state folds into a snapshot (lastIncludedIndex) and older log entries are truncated.

Distributed Consensus Glossary
TermDefinition in RaftLab
Quorum (Majority)Math.floor(N / 2) + 1 nodes (3 for 5 nodes, 2 for 3 nodes). Prevents split-brain commits.
Write-Ahead Log (WAL)Durable append-only log + term/vote/snapshot keys persisted in Upstash Redis (or in-memory fallback).
Network Partition (Isolate)Blocks RPCs for a node so a minority side cannot commit while a majority side can elect/commit.
Idempotent WriteDeduplicates retries carrying the same requestId so network retries do not double-apply mutations.
Service Boundaries & Deployment Trade-offs
  • Static Dashboard (Vercel): Zero server state; talks purely over HTTP and SSE to the Gateway URL.
  • Gateway (:5000): Aggregates /status, routes writes with leader redirect retry, returns 503 when leaderless, and streams SSE events.
  • Raft Nodes (N1-N5): Independent state machines with randomized election timeouts (1500-3000ms) and periodic heartbeats/replication.
  • Cloud Datastore (Upstash Redis): Externalizes durability across container restarts so revived nodes recover term, votes, log, and snapshots.
